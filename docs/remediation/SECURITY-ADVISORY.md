# Security advisory — applications generated with `@techunico/node-framework` ≤ 0.4.0

**Status:** fixes exist on branch `fix/stabilization` (unreleased; to be published after 0.4.0). **Generated applications do not update
themselves**: the framework is copied into each application at generation time, so every existing
application must be patched individually.

**Unresolved operational risk:** whether any affected application is deployed to production is not
known to this repository. The owner must confirm the inventory below.

---

## 1. Summary

| ID | Severity | Issue | Affected |
|---|---|---|---|
| TA-1 (F-01) | Critical | Admin JWTs can be forged: admin tokens are signed with the hardcoded key `secret_admin`, and the verification key is chosen from the token's own (unverified) `userType` claim | Every generated app; exploitable wherever admin tokens or `userType`-based decisions are used |
| TA-2 (F-05) | Critical | Default `JWT_SECRET=SUPERSECURESECRET` shipped in `.env.example` and copied into `.env`. Anyone can sign user tokens for an app that kept it | Every app that did not change `JWT_SECRET` |
| TA-3 (F-06) | High | No `.gitignore` in generated apps, so `.env` (secrets) may be committed | Every generated app |
| TA-4 (F-04) | Critical (payments) | Payment plugin silently uses the mock gateway when Razorpay keys are missing — **including in production** — and the mock accepts the signature `"mock-valid"` or an unkeyed hash | Apps with `PLUGINS` containing `payment` (framework ≥ the geo/payment commit `514b02c`) |
| TA-5 (F-17) | Medium | The auth guard logs the full `Authorization` header (bearer token) when the scheme is not exactly `Bearer` | Every generated app |

## 2. Identify affected applications

An application is affected if it was generated by this CLI (any version up to 0.4.0). Indicators:

```bash
# Run inside a candidate application
grep -n "secret_admin" src/plugins/jwt.plugin.ts          # TA-1
grep -n "^JWT_SECRET=SUPERSECURESECRET" .env .env.example  # TA-2 (also check deployed secrets)
git ls-files .env                                          # TA-3: prints ".env" if it is committed
git log --all --oneline -- .env                            # TA-3: was it ever committed?
grep -n '"mock-valid"' src/plugins/payment/providers/mock.provider.ts   # TA-4
grep -n "authHeader }" src/core/auth.guard.ts              # TA-5
```

Also check the **deployed** environment (secret manager, CI variables, container env), not only files:
`JWT_SECRET` equal to `SUPERSECURESECRET` or shorter than 32 characters; `NODE_ENV=production` together
with `PLUGINS` containing `payment` and empty `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`.

## 3. Remediation per application

Apply in this order. Each step lists how to verify it.

### 3.1 Replace the JWT implementation (TA-1)

Applications generated by ≤ 0.4.0 do not have the new `app.config` plumbing, so copy the
self-contained pieces and adapt two files:

1. Copy `src/core/jwt.ts` from the fixed framework (it depends only on `jsonwebtoken`) and install
   its types: `npm install -D @types/jsonwebtoken@^9.0.10` (older generators did not add them).
2. Copy `src/core/auth.guard.ts` (adds `authorize()`, stops header logging) and add
   `TOKEN_EXPIRED: 'TOKEN_EXPIRED'` to `src/core/error-codes.ts`.
3. Replace `src/plugins/jwt.plugin.ts` with:

   ```ts
   import fp from "fastify-plugin";
   import { config } from "@/config";
   import { createJwtService } from "@/core/jwt";

   export default fp(async (app) => {
     app.decorate("jwt", createJwtService({
       secret: config.jwt.secret,
       adminSecret: process.env.JWT_ADMIN_SECRET || undefined,
       issuer: process.env.JWT_ISSUER ?? "techunico",
       audience: process.env.JWT_AUDIENCE ?? "techunico-api",
       accessTtl: process.env.JWT_ACCESS_TTL ?? "15m",
       refreshTtl: process.env.JWT_REFRESH_TTL ?? "30d",
     }));
   }, { name: "jwt" });
   ```

4. In `src/config/env.schema.ts` require a strong secret, e.g.
   `JWT_SECRET: z.string().min(32).refine((v) => !/supersecuresecret|changeme|secret_admin/i.test(v))`.
5. Make sure every `jwt.sign(...)` call passes the user type and `"access"` / `"refresh"`
   (`auth.controller.ts` in generated apps already does).

These steps were verified on a copy of an application generated in June 2026 (pre-0.4.0): the
patched files type-check, a token signed with `secret_admin` is rejected (401), a newly issued user
token is accepted (200), and `JWT_SECRET=SUPERSECURESECRET` fails startup.

If the app customised `getSecret`/`signToken`, port the customisation to `createJwtService`; do
**not** keep any code path that picks a key from a decoded-but-unverified claim.

Verify: a token signed with `secret_admin` is rejected:

```bash
node -e '
const jwt=require("jsonwebtoken");
console.log(jwt.sign({id:"1",role:"admin",userType:"admin",tokenType:"access"},"secret_admin",{expiresIn:"5m"}))'
# then: curl -H "Authorization: Bearer <token>" http://localhost:3000/api/v1/auth/me   → 401
```

### 3.2 Rotate keys (TA-1, TA-2) — required

Patching code is not enough: any token signed with a known key may already be in an attacker's hands.

1. Generate new secrets (never reuse the old values):
   ```bash
   node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"   # JWT_SECRET
   node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"   # JWT_ADMIN_SECRET (only if admin tokens are used)
   ```
2. Set them in every environment's secret store. The fixed app refuses to start with a missing,
   short or placeholder secret.
3. Optionally set `JWT_ISSUER` / `JWT_AUDIENCE` per application or environment so tokens cannot be
   replayed across apps that might share a key.

**Token invalidation:** after deployment, **all existing tokens are rejected** (new key, new `kid`,
`iss`/`aud` claims). Every user, including admins, must sign in again; refresh tokens stop working.
Plan this as a forced re-authentication and inform clients (mobile apps should handle 401 by
returning to login).

### 3.3 Audit for misuse (TA-1, TA-2)

Before rotation, preserve logs. Look for requests authenticated as admin (or as unexpected users)
that do not correspond to real logins. With the old code, `ctx.user.type === "admin"` came straight
from the token; review any data changed by admin-only endpoints.

### 3.4 Secrets in git (TA-3)

1. Add a `.gitignore` (copy `packages/create-techunico-app/scaffold/_gitignore` as `.gitignore`).
2. If `.env` was ever committed (`git log --all -- .env`), treat every secret in it as leaked:
   rotate database passwords, JWT keys, Razorpay keys, Cloudinary and Google API keys. Removing the
   file from history is optional and does not un-leak the values.
3. `git rm --cached .env` and commit.

### 3.5 Payments (TA-4)

1. Copy `src/plugins/payment/{config.ts,plugin.ts,types.ts,errors.ts,providers/mock.provider.ts,providers/razorpay.provider.ts}`
   and `src/core/safe-error.ts`. In ≤ 0.4.0 apps register the plugin with an explicit config
   (they have no `app.config`):
   `await app.register(PaymentPlugin, { config: loadPaymentConfig(process.env) })`
   (`loadPaymentConfig` from `./payment/config`).
2. In production set `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET`. The fixed
   plugin refuses to start in production without valid keys and never registers the mock gateway.
3. **Audit:** if an affected app ran in production with the payment plugin and without Razorpay keys,
   every order/payment recorded during that period was processed by the mock gateway. Reconcile
   those records against the Razorpay dashboard; treat any "paid" state that has no Razorpay
   counterpart as unpaid. Check webhook endpoints for requests with `signature: "mock-valid"`.
4. Webhook controllers must pass the **raw request body** to `payment.verifyWebhook`; re-serialised
   JSON may not match Razorpay's signature.

### 3.6 Logging (TA-5)

Copy `src/core/auth.guard.ts` and `src/core/log-redaction.ts`, and add
`redact: loggerRedaction` to the existing `loggerConfig` in `src/config/logger.ts`. Purge or restrict
access to existing logs that may contain bearer tokens; tokens issued under the old key are
invalidated by 3.2 anyway.

## 4. Verification checklist (per application)

- [ ] `grep -rn "secret_admin\|secret_user\|SUPERSECURESECRET\|mock-valid" src .env.example` → no matches
- [ ] App refuses to start with `JWT_SECRET=SUPERSECURESECRET`
- [ ] Forged admin token (3.1) → 401; a fresh login token → 200 on `/api/v1/auth/me`
- [ ] Old tokens issued before rotation → 401
- [ ] `git ls-files .env` prints nothing
- [ ] Production with `PLUGINS=payment` and no Razorpay keys → startup fails
- [ ] Logs for a request with `Authorization: bearer <token>` do not contain the token
